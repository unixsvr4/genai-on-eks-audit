# Gotchas — everything that wasn't in the workshop instructions

Every item here was hit **live**, verified against real command output, and is cited to the exact spot in [`RESEARCH.md`](../RESEARCH.md) where it happened. It is collected here in full because any write-up of a run like this can only carry a fraction of it.

## EKS Auto Mode & cluster setup

- **GPU nodes truly scale to zero.** `kubectl get nodepool/gpu` showed `NODES: 0` right up until the first pod requesting `nvidia.com/gpu` was scheduled — Auto Mode doesn't idle-park GPU capacity. First GPU node took ~30s–1min to go Ready from a cold NodePool.
- **`checkip.amazonaws.com` must be queried from your local browser, not the workshop IDE terminal** — the IDE is itself an EC2 instance, so `curl`ing from inside it returns the *instance's* IP, not yours, and you'll lock yourself out of your own ALBs.
- **`IngressClassParams.inboundCIDRs` overrides every individual Ingress's own `inbound-cidrs` annotation.** Several manifests in this workshop request `0.0.0.0/0` directly on the Ingress — that request is silently capped by the cluster-wide restriction set once, early on. Don't assume an Ingress annotation is the actual source of truth for who can reach it.
- **The Grafana admin password is a hardcoded chart default** (`notforproductionuse`), not randomly generated. Fine for a 4-hour demo; would be a real finding in a security review of anything longer-lived.
- **An unfiltered `aws ec2 describe-instances` silently excludes EKS Auto Mode's own worker nodes.** They carry `"Operator": {"Managed": true, "Principal": "eks.amazonaws.com", "HiddenByDefault": true}` in the API response, and AWS omits operator-managed resources from a blanket Describe call by default — confirmed live, same account/region/moment: `describe-instances --instance-ids <id>` found the node fine, the unfiltered call returned zero `Reservations`. Query by explicit instance ID (an EKS Auto Mode node's name **is** its EC2 instance ID, so `kubectl get nodes` gives you exactly what you need) rather than scanning the whole account. Cost this repo real debugging time in `scripts/real_cost_of_cluster.sh` — see that script's comments for the fix.

## vLLM / model serving

- **`served-model-name` isn't set by default** — without it, vLLM's `/v1/models` and every client request has to address the model by its raw S3 URI (`s3://bucket/Ministral-3-8B-Instruct-2512/`). Set it explicitly or your OpenAI-API clients get an ugly model identifier.
- **DCGM shows ~40GB "used" on a 46GB GPU at 0% utilization** — this is not a leak. vLLM pre-allocates its entire KV-cache pool upfront at startup (the whole point of PagedAttention's memory-pool strategy), so the framebuffer looks "full" long before any request has been served.
- **The saturation benchmark reveals a real, concrete scaling ceiling**, not a hand-wavy one: staged load at 5→10→20 req/s on a single L40S showed TTFT holding steady through 10 req/s (~70ms) then **doubling to 160ms at the 20 req/s stage**, with achieved throughput falling further short of the target rate at each step up. That's the actual moment to point to when explaining "why do we need to scale out" instead of guessing.

## Observability (Prometheus / Grafana)

- **`release: kube-prometheus-stack` is a hard requirement on every ServiceMonitor/PodMonitor**, confirmed three separate times (DCGM's Helm-generated one, a hand-written one for vLLM, and Ray's PodMonitors). Miss this label and the Prometheus Operator silently ignores the object — no error, just no data.
- **Pre-provisioned Grafana dashboards can exist long before the thing they visualize does.** The Ray Grafana dashboards were present and "39h old" from the very start of the workshop, sitting empty until the Ray/KubeRay module — several modules later — finally gave them a data source. If you see dashboards for a component you haven't deployed yet, it's often just sequencing, not a bug.

## LMCache / KV-cache tiering

- **`pip install lmcache==0.3.8` fails on every run** (PyPI's version list jumps `0.3.7 → 0.3.9`) — but the container already has a working version pre-installed (`0.3.13` in this run), so this red error line in the logs is cosmetic. Don't chase it.
- **`PYTHONHASHSEED` must be set explicitly in production** — LMCache's own logs warn that its default hash implementation isn't consistent across process restarts without it, which would silently break cache-key consistency in a real multi-replica deployment.
- **ElastiCache Serverless Valkey needs its own dedicated `cleanup-valkey.sh`.** `kubectl delete pod` only removes the Kubernetes side; the actual AWS cache resource and its security group keep billing until you run the AWS-side teardown separately.
- **`CreateServerlessCache` throwing `InvalidCredentialsException` on the first attempt is a known transient flake**, not a real credentials problem — the setup script is idempotent about the security group, so it's safe to just retry once.

## Ray Serve / KubeRay

- **The Ray/KubeRay manifests are pinned to noticeably older repo tags** than the plain-vLLM path in the same sample repo (`v2.3.x` vs `v2.4.x`–`v2.5.x`) — the two serving paths are clearly maintained somewhat independently even though they live in one repo.
- **A RayService creates three Kubernetes Services with overlapping-but-different port sets** (`vllm`, `vllm-head-svc`, `vllm-serve-svc`) — know which one to actually point clients at. It's `vllm-serve-svc:8000`, deliberately the same Service name the plain-vLLM path used, so nothing downstream (Open WebUI, RAG service) needs to change when you swap serving frameworks underneath it.

## RAG, fine-tuning, and the failures worth documenting honestly

- **The single biggest gotcha of the whole workshop**: an S3-backed PersistentVolume (via the Mountpoint-for-S3 CSI driver) depends on **live IAM credentials for the entire lifetime of the mount**, unlike the Run:ai Model Streamer approach used everywhere else, which only needs credentials at model-load time. When the workshop's temporary AWS session started expiring mid-"Customize Model," this is exactly the resource that broke first — a pod stuck in `ContainerCreating` for 37+ minutes with no useful error.
- **The tell that credentials are expiring is oddly indirect**: `aws s3 ls` on a bucket you already know the name of failed with `AccessDenied` on `s3:ListAllMyBuckets` — a permission that has nothing to do with listing objects in a known bucket. If you see that specific mismatch, suspect session/IAM expiry before anything else.
- **A stuck pod produces a cascade of misleading downstream errors**: `port-forward` correctly refuses ("pod is not running"), and every subsequent `curl` to that port returns an empty body, which a JSON parser reports as `Expecting value: line 1 column 1` — easy to misread as an API bug when the real story is "nothing is listening."
- **Services get reused by name across modules on purpose** — the RAG service's `MODEL_ENDPOINT` points at the same `vllm-serve-svc:8000` name used since "Serve a Model." If a previous module's model deployment never came up, the RAG service and its Gradio UI will still deploy cleanly and report `Running` — they just have no backend to actually answer a query. A clean `kubectl rollout status` does **not** mean the feature works end-to-end.
- **Stray local `port-forward` processes accumulate over a long session.** A "port already in use" error, followed by a `curl` that returns a confusing 404, usually means you hit some *other* stale forwarded service on that port, not the one you intended — check `lsof -i :<port>` before reusing a port number.

## AWS billing & account structure

- **An On-Demand Capacity Reservation you create yourself bills at the on-demand rate for the reservation's active duration, whether or not a matching instance is actually running in it** — but you're not double-charged when one is. Total GPU cost is effectively `(hours the ODCR exists) × (hourly rate)`, which is why setting `--end-date-type limited` up front matters more than trying to optimize GPU utilization within the window. See [`COST.md`](./COST.md).
- **In the AWS-hosted workshop event specifically, the GPU capacity reservation lived in a separate AWS-operator account** from the attendee's own ephemeral account (`cancel-capacity-reservation` failed with `UnauthorizedOperation` against an ARN in a different account ID) — a deliberate shared-pool design so no single attendee can release capacity out from under others. This doesn't apply when you own the ODCR yourself, as this repo's reproduction does.
- **`terraform destroy` failing with "command not found" at the end of an AWS-hosted event is expected, not a bug** — the cleanup script is shared boilerplate between the self-paced and at-event instructions; at an event, the base cluster/VPC teardown is AWS's own responsibility when the event's stack is torn down, not something attendees run themselves.

## Reproducing this repo in a fresh AWS account

- **An account on the new Free Tier *plan* can only launch six instance types, and that does not expire.** This is the single most expensive gotcha in the repo; it took nine rounds of diagnostics to characterise correctly. If `aws freetier get-account-plan-state` reports `accountPlanType: FREE`, the account may launch **only** the types returned by `aws ec2 describe-instance-types --filters "Name=free-tier-eligible,Values=true"` (on the reference account, in `us-east-2`: `c7i-flex.large`, `m7i-flex.large`, `t3.micro`, `t3.small`, `t4g.micro`, `t4g.small`). Everything else is refused with `errorCode: InvalidParameterCombination`, `errorMessage: "The specified instance type is not eligible for Free Tier..."` — and `CreateFleet` returns **HTTP 200** with that buried in `errorSet.item`, so nothing at the Kubernetes, Terraform, or EC2-API-status layer shows it. Only a raw CloudTrail `CreateFleet` event body does.
  - **It is not a temporary new-account hold, and waiting does not fix it.** Rounds 1-7 of `DIAGNOSTICS*.md` concluded it was transient because `general-purpose` eventually produced a node. It wasn't: Karpenter's `system`/`general-purpose` pools accept a wide instance-type range, so they churn until they land on `c7i-flex.large` — which *is* eligible — and then look healthy forever. The `gpu` NodePool is pinned to exactly `g6e.2xlarge`, has no fallback, and can never succeed. That asymmetry is why `01-deploy-infra.sh` works on a FREE plan and `02-gpu-infrastructure.sh` cannot.
  - **It is independent of service quotas.** The reference account held a granted 16-vCPU `L-DB2E81BA` GPU quota and still could not launch one `g6e`. Eligibility is evaluated before quota.
  - **Do not try to detect it with a dry-run.** `run-instances --dry-run`, `create-fleet --dry-run`, and Karpenter's own internal CreateFleet dry-run were all measured against a provably-blocked `g6e.2xlarge` and all three returned success. `create-fleet --dry-run` even succeeds with a launch-template ID that does not exist. `00-prereqs.sh` gates on the account plan + eligible-type set instead, which is authoritative and free — and it now *stops* on a FREE plan rather than warning, because the next script along bills real money to build a cluster the GPU node can never join.
  - **Fix**: `aws freetier upgrade-account-plan --account-plan-type PAID` (or Billing console → Free Tier → *Upgrade to a paid plan*). Full trail: `DIAGNOSTICS0.md` → `DIAGNOSTICS8.md` at the repo root; `DIAGNOSTICS8.md` has the root cause and corrects the earlier rounds.
- **`kubectl describe nodeclaim` can't catch the failure in the act.** In this account's churn, a new `general-purpose-*` NodeClaim was created roughly every 90 seconds and torn down before ever reaching a terminal `Launched=False` condition — `describe` only ever caught the *next* one at `~49s` old, still `AwaitingReconciliation`. The real error lives one layer down, in the EC2 API response, not in anything Kubernetes-visible.
- **The `errorCode`-substring CloudTrail filter is a trap.** Filtering `lookup-events` output for JSON containing the literal text `"errorCode"` matches essentially every event in the account, because CloudTrail includes that key (often `null`) on successful calls too. Read one full, unfiltered event body (`jq .` on the whole `CloudTrailEvent`) instead of trying to filter for errors client-side.

- **`InsufficientInstanceCapacity` on `CreateCapacityReservation` is a statement about one Availability Zone, not the region.** An ODCR is AZ-scoped. GPU capacity runs out per-AZ, so a request pinned to a single zone can fail while two other zones in the same region have the instance type free — and the AWS CLI's own `(reached max retries: 2)` retries the *same* zone, which is the one retry that cannot help. Derive candidate AZs from `ec2 describe-instance-type-offerings --location-type availability-zone` intersected with the AZs of the cluster's own subnets (`eks describe-cluster` → `ec2 describe-subnets`); both calls are free. Retry across zones only for capacity errors — auth/quota/parameter errors fail identically everywhere.
- **An ODCR refused for lack of capacity in every AZ does NOT mean you cannot launch the instance.** Measured live: `CreateCapacityReservation` returned `InsufficientInstanceCapacity` in all three `us-east-2` AZs, and seconds later Karpenter launched the same `g6e.2xlarge` on-demand in `us-east-2b` — one of the zones that had just refused. Reserving capacity is a strictly harder ask than consuming it: a reservation makes AWS set capacity aside and hold it, a launch only needs a slot at that instant. Never treat a failed reservation as proof the region is out of GPUs.
- **An ODCR is a capacity *guarantee*, not a prerequisite for a GPU node — and skipping it costs less, not more.** The workshop's `gpu` NodePool lists `karpenter.sh/capacity-type In ['reserved', 'on-demand']`, so Karpenter launches fine without any reservation. An ODCR bills from creation for its full duration whether or not an instance ever occupies it (see `docs/COST.md`), whereas with no reservation nothing bills until a node actually exists. So "no capacity anywhere" is a degraded mode worth continuing through, not a reason to abort — but clear `capacityReservationSelectorTerms` off the NodeClass when you do, or Karpenter waits on a reservation that does not exist instead of falling back to on-demand.

- **A label selector matches the OLD ReplicaSet's pods during a rollout, so "is any pod failing?" is the wrong question.** Any health check that selects on the app label will see the pod it is replacing. If you are redeploying precisely *because* the previous revision was broken — the common case — the dying pod's `CrashLoopBackOff` will be attributed to the new one. Filter out pods carrying `metadata.deletionTimestamp` and judge only the newest by `creationTimestamp`.
- **Test a teardown verifier while the infrastructure is still UP.** A check that always reports "clean" is worse than no check, and you cannot tell the two apart by running it after a successful destroy — both print the same thing. Run it against the deployed cluster first and confirm it names what is actually there. Doing that here also exposed the Auto Mode blind spot in the same output: the instance check printed `clean` while three nodes ran, one a `g6e.2xlarge` at $2.24/hr.
- **Rootless BuildKit cannot run on Bottlerocket, and the error blames the disk.** EKS Auto Mode uses Bottlerocket, which sets `user.max_user_namespaces=0`, so rootlesskit cannot create its namespace: `/proc/sys/user/max_user_namespaces needs to be set to non-zero` followed by `failed to start the child: fork/exec /proc/self/exe: no space left on device`. That ENOSPC is the user-namespace limit refusing the clone, **not** ephemeral storage — do not go looking at disk. Either run privileged, or use a builder that needs no user namespaces at all: kaniko snapshots layers in its own filesystem and runs unprivileged with no securityContext (accepting that it is archived upstream).
- **A ConfigMap volume is a symlink farm, so `COPY` from one silently produces a dangling link.** Every key is materialised as a symlink into a hidden `..data/` directory. kaniko copies the symlink rather than dereferencing it, and the build fails later reporting the file as simply missing (`Could not open requirements file: [Errno 2] No such file or directory`) even though it is mounted and readable. Stage the context through an init container with `cp -rL` into an `emptyDir`.
- **If a cluster is already running, build the image on it rather than on a laptop.** Not a purity argument — a measured one. Of this repo's four live failures in the image-building module, three were properties of the developer machine and none were AWS problems: the Docker daemon was not running (and `docker login` succeeded anyway, so the run reported success one line before failing), the daemon *was* running but the docker context pointed at a socket that did not exist, and the image was built for the build host's architecture. Building in-cluster removes the class rather than fixing the instances: there is no daemon to be down, no context to be wrong, and the build architecture **is** the run architecture. A ~4KB build context fits in a ConfigMap, `aws ecr get-login-password` in a short-lived Secret covers the push with no new IAM, and everything created dies with the cluster — so unlike CodeBuild it adds nothing to the teardown surface.
- **`exec format error` in a pod means the image architecture does not match the node.** Building on Apple Silicon without `--platform` produces an arm64 image; EKS Auto Mode's general-purpose nodes are amd64, and the pod dies with `exec /usr/local/bin/python: exec format error`, which says nothing about architecture. The build log is the tell — aarch64 wheel names (`..._aarch64.whl`). Worse, an EKS Auto Mode cluster is **mixed**: here the system pool ran `c6g.large` (arm64) and general-purpose ran `c6a.large` (amd64), so an unpinned image is wrong on one of them either way and placement is luck. Pin **both** halves — `docker build --platform linux/amd64` *and* `nodeSelector: {kubernetes.io/arch: amd64}` — because pinning only the image still allows scheduling onto the arm64 node, and pinning only the pod still ships the wrong binary.
- **`docker info` failing does NOT mean the daemon is down — check before you say so.** On this machine OrbStack was running and serving Docker 29.4.0 on `<home>/.orbstack/run/docker.sock`, while the active docker context was `default` pointing at `unix:///var/run/docker.sock`, which did not exist. `docker ps` failed with the identical "check if the daemon is running" message you get when nothing is running at all. Telling that user to start Docker is useless advice confidently delivered. Probe the known per-runtime sockets (OrbStack `<home>/.orbstack/run/docker.sock`, Colima `<home>/.colima/default/docker.sock`, Docker Desktop `<home>/.docker/run/docker.sock`, Rancher `<home>/.rd/docker.sock`) and distinguish "not running" from "client pointed elsewhere" — `docker_daemon_check` in `scripts/lib/env.sh`. The fix for the second case is `docker context create <name> --docker host=unix://<socket>` then `docker context use <name>`.
- **`docker login` against ECR succeeds with no Docker daemon running, so "Login Succeeded" is not evidence Docker works.** Login only writes a credential into the local docker config; it never touches the daemon. The build on the very next line then fails with `failed to connect to the docker API at unix:///var/run/docker.sock`, which reads as an ECR or auth problem and is not one. `command -v docker` is equally useless as a readiness check — it proves the CLI is installed, nothing more. Check `docker info` instead, and check it *before* the login so the failure lands where it belongs.

- **`kubectl get --timeout=120s` is not a thing, and `2>/dev/null || echo "<default>"` will hide that from you forever.** `--timeout` is a valid flag for `kubectl wait`, not for `kubectl get` — `get` errors with `unknown flag: --timeout` and exits non-zero. Wrapped in `$(... --timeout=120s 2>/dev/null || echo "pending")`, that produced a confident `Grafana: http://pending` on **every** run of this repo, indistinguishable from an ALB that was genuinely slow. It was never a race. If you need to wait for a field to be populated, write an explicit poll loop; and be very suspicious of any `2>/dev/null || echo <plausible default>`, which converts a broken command into a plausible answer.
- **An ALB takes roughly 40s to publish its hostname, so reading it straight after `kubectl apply` always returns empty.** The AWS Load Balancer Controller must see the Ingress, create the ALB, and write back `.status.loadBalancer.ingress[0].hostname`. Measured live: 39s. Poll for it (`lb_hostname` in `scripts/lib/env.sh`); on GKE/AKS read `.ip` instead of `.hostname`.
- **`kubectl port-forward` EXITS when the far end is not listening — it does not retry.** `error: lost connection to pod` after `An error occurred forwarding ... connection refused` means the forward gave up, so any `PF_PID` you saved is already dead and the `curl` that follows talks to nothing. A wrapper that restarts the forward until the endpoint answers (`pf_start`) is the fix; accept *any* HTTP status as readiness, since a 404 still proves a server is listening and not every service exposes `/health`.
- **A vLLM pod reads `1/1 Running` for the entire model load, because the workshop's deployment declares no readinessProbe.** `phase == Running` means the container process started; vLLM then pulls ~9.7GB from S3, loads it onto the GPU and initialises the KV cache before binding `:8000`. Measured live: pod `Running` at `08:34:29`, `Application startup complete` at `08:35:38` — a **69-second** window in which every Kubernetes signal says healthy and the server does not exist. Never gate a test on `phase == Running` plus a fixed sleep; poll `/health` instead:
  ```bash
  kubectl exec deploy/mistral -- curl -sf -o /dev/null --max-time 3 http://localhost:8000/health
  ```
- **`kubectl port-forward` reporting `connection refused` *inside the pod's own netns* usually means "too early", not "broken networking".** The full error (`failed to connect to localhost:8000 inside namespace "..." ... connect: connection refused`, then `error: lost connection to pod`) implicates the CNI and reads like an infrastructure fault. It is the forward working correctly and faithfully reporting that nothing is listening on the far end yet. Check whether the server is actually up before debugging the network.

## The model-download Job (three stacked upstream bugs)

All three confirmed live at upstream tag `v2.5.2`, all three now patched at clone
time by `00-clone-terraform.sh`. Full trail: `DIAGNOSTICS9.md`.

- **EKS Pod Identity is injected at pod *admission*, and a `depends_on` is not enough to win that race.** The webhook looks up an existing association once, when the pod is admitted; a pod admitted before the association is visible never gets an `eks-pod-identity-token` volume and can never recover — the AWS CLI inside it reports `NoCredentials` with an *empty* current role (Bottlerocket blocks IMDS from pods, so there is no node-role fallback either). Upstream **already has** `aws_eks_pod_identity_association.model_storage` in the Job's `depends_on`; the measured overlap was `association createdAt 14:46:23.141Z` vs `pod creationTimestamp 14:46:23Z`. `CreatePodIdentityAssociation` returns success before the association is visible to the admission path, so no Terraform ordering fix exists for it. Diagnose with the pod's volume list — `eks-pod-identity-token` present or absent is the whole answer:
  ```bash
  kubectl get pod -n default -l job-name=model-download -o jsonpath='{.items[0].spec.volumes[*].name}'
  ```
- **A validation sidecar under `restartPolicy: Never` cannot fail its own pod.** Upstream anticipated the race (`backoffLimit: 10`, and the validator literally prints *"Pod will be recreated to retry Pod Identity association"*) but made the validator a **sibling** of the long-running download container. A Job replaces a pod only when the pod *fails*, and a pod fails only when **all** containers terminate — so while `download` runs for ~40 minutes, the pod stays `Running`, the retry never fires, and `backoffLimit` is dead code. The fix is `initContainers`, which both gates the download and makes the existing retry work. Generalises: **any** validation container that is expected to fail the pod must be an initContainer, never a sidecar.
- **Karpenter will consolidate a node out from under a long batch job to save cents.** A ~16GB download with `Mounts: <none>` was evicted six minutes in for a `$0.20/hr` saving (`Disrupting Node: Underutilized` → `Evicted pod: Underutilized`), losing all progress; the replacement pod restarts from zero. Since `activeDeadlineSeconds` counts from **Job creation, not pod start**, every restart is charged against the same budget, so the Job churns until it times out. Fix is the pod-scoped `karpenter.sh/do-not-disrupt: "true"` annotation on the pod *template* — it does not disable consolidation cluster-wide and lapses when the pod terminates. It works on an already-running pod, so it can rescue a download in flight. Note it only covers *voluntary* disruption; surviving a spot interruption needs a volume that outlives the pod.
- **`Running 0/1` is what both a healthy and a doomed Job look like.** For the ~40 minutes all of the above was going wrong, `kubectl get job` showed `Running 0/1` and the pod showed `1/2 NotReady`. There is no failing condition to alert on until the deadline fires. Two checks that actually distinguish them: the S3 destination stays at `Total Size: 0`, and the HuggingFace `Fetching 11 files: 0%` progress bar only advances on **whole-file** completion — so it reads `0/11` through most of a healthy multi-file pull too. To tell them apart, measure bytes directly:
  ```bash
  kubectl exec -n default <pod> -c download -- sh -c 'F=$(find /tmp -name "*.incomplete"|head -1); A=$(stat -c %s "$F"); sleep 30; B=$(stat -c %s "$F"); echo $(( (B-A)/30/1024/1024 )) MB/s'
  ```

## General workshop-repo hygiene

- **The upstream sample repo is pinned to at least 7 different tags across one workshop's manifests** (`v2.3.1`, `v2.3.2`, `v2.4.7`, `v2.4.8`, `v2.5.0`, `v2.5.1`, `v2.5.2` all appear), sometimes even **within the same module** (dataset from one tag, job manifest from the next tag up). If you're reproducing this outside the live event, pin the *exact* tag each command used — don't assume `main`/latest is safe, and don't assume one tag covers the whole workshop.
